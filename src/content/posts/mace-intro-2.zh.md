这篇文章回答的问题是：mace 为什么是这个形状，以及每个形状的代价是什么。

- 想知道 mace 怎么用、多快，看 [README](https://github.com/abbycin/mace)
- 想改 mace 的代码，看 `docs/design.md`（流程规范）和 `docs/constraints/registry.yaml`（不变式台账）
- 想判断一个改动该不该做，看这篇文章

## 设计目标与优先级

先说清楚 mace 不追求什么，因为不追求的东西比追求的更能约束设计。

mace 是嵌入式引擎，单进程，不做分布式，不做 SQL，不做多租户隔离，也不做跨节点的副本或共识。这些不是"以后再做"，而是明确排除：一旦引入节点间通信，前面所有关于崩溃窗口的推理都要重写。

在剩下的目标里，优先级是这样的：

1. **崩溃安全与数据不丢**。这是唯一不能妥协的。任何性能优化如果要求放宽持久化边界，直接否决。
2. **快照隔离的语义正确**。已提交事务在崩溃后必须仍然可见，已中止事务必须仍然不可见。
3. **吞吐与延迟**。在 1、2 不被破坏的前提下优化。
4. **实现简单**。这条排最后，但它是个真实的约束：mace 目前有效代码在 20K 左右，已经不是"简单了"，当然这也是长期的工作重点

第 1 条和第 2 条的保证有一个前提：持久化选项必须保持默认开启。开启时每次提交都要求 WAL 真正落盘，崩溃后已提交的事务一定还在。另一个体现是正常退出时，即使全程用的是宽松模式，最后一次 checkpoint 仍然对所有输出文件做完整同步——运行中可以放松，退出时不能，因为退出之后再没有 WAL 可以指望了。

## 真正的难点在哪里

不是索引，不是事务，是**几个阶段之间的状态交接**。

### checkpoint 收集的是可达集，不是脏集

这一节是我在 mace 里最想讲清楚的一个取舍，因为它决定了 checkpoint 到底是什么。

一个直觉的做法是：checkpoint 把所有脏页收集起来写出去。这在页不可变且写者不改变页可达性的模型里是成立的，比如 LSM 树的 memtable。但 Bw-Tree 不行。一个页变脏之后、在 checkpoint 跑到它之前，它完全可能已经不可达了：增量链被合并、父节点的链接被换成新页、节点分裂或合并产生了新的页镜像。这些页如果照写，就是纯垃圾——写放大白付，而且它们会在下一次 GC 里被当成需要回收的空间。

所以 mace 的 checkpoint 收集的是**从脏根出发可达的页集合**，不是脏页集合。下面把这个集合叫**写集**，它是本次 checkpoint 要写进 data 和 blob 文件的那批页。

> 那为什么不干脆用 arena？既然逻辑地址是单调递增分配的，把脏区当成一段连续内存整段刷出去，不就把遍历省掉了？
>
> 不能这么做的原因在 Bw-Tree 本身：**页是整页替换的**。一次合并产生新的基础页、旧的那一页整页作废；一次分裂把一个节点变成两个，原来那一页也随之作废。于是任意时刻，一个预留的连续区间里都有相当大比例的槽位装着已经被取代的死页。
>
> 换句话说，**arena 的有效载荷率很低**：预留空间必须按峰值给，而峰值里很大一部分是垃圾。mace 反过来做——每个页独立分配、独立释放，页一旦不可达就还回去，内存占用跟着**存活数据**走，而不是跟着某个预留区间走。
>
> 代价是地址空间不再连续，于是"哪些页还活着"这个问题没法靠扫描区间回答，只能靠可达性遍历。

#### 遍历还必须算出两个记账值

第一个是**持久化边界**（frontier）。恢复时要决定一条 WAL 记录是否有必要重放：如果它对应的更新已经落进持久页，就跳过。frontier 就是回答这个问题的依据。它按 bucket 记，每个写者组一个位置，定义是：

> 每个 bucket 的写集里所有页所覆盖的更新位置，按写者组取最大值。

它有方向性，这一点决定它只能这么算：

- 报**高**了，恢复会跳过一些其实还没落盘的更新 → **丢数据**
- 报**低**了，恢复会重放一些其实已经落盘的更新 → 白做功，不丢数据

代价不对等，所以它宁可报低也不能报高。而它只能从写集算出来——按脏页算，就会把那些根本没进写集的死页上的更新也算进去，于是报高、丢数据。

第二个是垃圾记账。写集里每个基础页身上都挂着它取代掉的那些旧地址，这些地址可以从账上退休；哪些能退、哪些还得留（本次 checkpoint 期间才产生的、或者比分割时已分配到的最大地址还新的），也只能从写集上读出来。

这两个值，加上"写哪些页"和"从页表上摘掉哪些页"，一共四样，互相依赖。

这一节的代价总结成一句：可达性遍历让 mace 少写很多垃圾页，换来的是 checkpoint 比枚举脏页贵，同时 frontier 和垃圾记账的正确性完全依赖这次遍历没有漏项。

### GC 和 checkpoint 会同时修改同一份记账

垃圾回收的部分重写要挑 victim 文件、读它们的非活跃记录、生成替换文件、发布替换记账、然后删旧文件。与此同时 checkpoint 也在产生新的垃圾地址，也需要更新非活跃位图和文件统计。

难点在于"归属"：checkpoint 在重写进行期间新退休的那些逻辑地址，应该记在旧文件的账上，还是记在新文件的账上？

常见的解法是加一把互斥锁，一方交接完另一方才能动。但这把锁会横跨整个重写过程，而重写可能持续很久，期间所有 checkpoint 都被阻塞，写者的脏数据无限堆积，反过来又推高重写压力。

mace 的选择是不加锁，靠"谁持有归属登记"来判定：重写在读取旧文件的非活跃状态之前就登记自己对这些文件的归属，checkpoint 遇到已被登记的文件时，走一条和普通路径不同的分支：重新解析逻辑地址、更新旧文件的账、把这个地址挂起来等重写方接收；重写完成后，已经被复制过去的地址再转到新文件的账上。归属状态只有在持久元数据和运行时记账都指向新文件之后才释放。

代价是这个交接的正确性不再由锁保证，而由"登记先于读取"这个顺序保证，顺序错了就是空间泄漏或者统计为负，而且要跑很久才看得出来（当然，mace 规划了泄漏的兜底措施，将在后续版本上线）。

### 中止清理不是撤销，是重写

中止的事务不能靠反向操作撤销，mace 的做法是把受影响的版本靠重写页面物理删掉。这带来两个额外约束：重写完成后还需要等可能持有旧页镜像的读者排空，任务才能真正结束（WAL 保留在此之前一直挂着）；另外，一个已经卸载的 bucket 不会为了稳态清理重新加载，它的任务保持未决状态并阻塞卸载和删除完成。完整取舍见后文的决策一节。

## 概念与身份模型

mace 有四层身份，这个分层是理解整个系统的关键。

| 身份 | 含义 |
| --- | --- |
| bucket ID | 一个命名 bucket 的持久身份 |
| page ID | bucket 内部某个索引页的逻辑身份 |
| logical address | bucket 地址空间内某个持久记录的持久身份 |
| file ID | 一个 data、blob 或 WAL 文件的身份 |

解析一个已持久化的页要走三步：bucket 的页表把页 ID 映射到逻辑地址，bucket 的区间图把逻辑地址映射到某个 data 或 blob 文件，文件内部的重定位表再把逻辑地址映射到字节范围。

为什么要多这一层间接？因为垃圾回收重写改变物理位置，但保持逻辑地址不变。代价是每次持久化都要维护区间图、重定位表和每文件统计这三张表，换来的是页引用和版本历史引用在文件重写前后完全稳定——这是重写能后台进行、不需要停写的前提。

持久化状态分四个域：元数据（除 WAL 之外的一切账本）、WAL 文件（事务重放记录和 checkpoint 提示）、data 文件（索引页和结构记录）、blob 文件（大 value）。元数据是重建数据库的核心，data 和 blob 只有通过元数据发布才真正属于数据库。

运行时分三个域：前台的事务和只读视图、bucket 运行时（索引、缓存、脏代、checkpoint 状态）、后台服务（checkpoint 完成、恢复、中止清理、WAL 回收、payload 回收、bucket 清理）。bucket 运行时是懒加载的，打开数据库不会把所有 bucket 的索引都拉起来。

## 借鉴与偏离

mace 的索引结构来自 Bw-Tree：不可变的页镜像加增量链更新，树变更发布新的页镜像而不是原地改持久页。增量链长度达到阈值就合并，阈值是每个 bucket 的可调项，默认取节点最大元素数的一半。

下面这些是刻意偏离常见做法的地方：

- **Bw-Tree 的 delta chain 在内存中不用链表**。内存里用一个 COW 的 B+ 树来组织增量，这样有两个好处：
  1. 查询性能有保障
  2. 对于 scan 来说可以缓存 node，对于点查询来说可以缩小锁的范围
- **数据插入并不是无锁的**。原版 Bw-Tree 的插入是对 delta chain 做 CAS 即可，但在高并发场景 CAS 会带来：
  1. Cache line ping-pong
  2. 大量的失败，导致其内存分配和拷贝全是无效操作
- **中止清理用重写而不是撤销**。反向操作需要为每种操作类型实现逆运算，这导致每次更新都需要写双份的 WAL 记录，mace 选择以稍微复杂的实现换取更小的写放大。
- **Merge Operator 是纯运行时对象，永不持久化**。引擎只持有运行时句柄，不记录 Operator 的身份，跨进程重启后的语义兼容性由调用方负责。这样避免了在磁盘格式里引入"如何表达用户自定义类型"这个问题。（不持久化的是算子本身；合并操作数是要写进 WAL 和页面的数据。）
- **关闭持久化选项时，写入系统页缓存仍然算有效**。这是选项的语义契约，不是不严谨。关掉它等于把上面第 1、2 条的保证转交给调用方自己负责；它默认开启，所以默认行为不受影响。

## 关键设计决策

这一节是全文的核心。每条决策我给出：备选方案、最终选择、理由、代价。"数据优先"是原则不是决策，我一开始就没有过备选，所以它只有理由和代价。

### 索引：为什么是 Bw-Tree 式的增量链

备选是 LSM 树（RocksDB 那条路）和传统 B+Tree 原地更新。

选 Bw-Tree 式结构的理由很简单：mace 既要 B+ 树的查询性能又要 LSM 树的写入性能。Bw-Tree 的页不是固定大小的，并且是 delta + base 的形式，可以减少写放大；它在前台就能执行 compaction，后台垃圾回收不需要做 key 的 merge，只需要重写有效数据；数据只有一层，查询不需要像 LSM 树那样跨多层。

代价是：对于冷数据，一次点查要先把整条增量链从盘上读出来。持久化时增量是通过页头的 `link` 串起来的链表，读 node 只能顺着 `link` 一个一个读，链越长读得越多。这也是必须有合并阈值的原因——链太长就合并。另外我早期在 photondb 上踩过一个坑：合并如果不保证同一个 key 的所有版本落在同一个节点上，查找路由会出错，频繁更新的单个 key 会让某个节点体积失控。mace 的处理是把版本历史放进 key 局部的历史区域，由一个描述符记录它从哪一页哪个槽开始、有多少个版本，不同 key 可以共享同一张历史页，但各自只在自己的声明范围内遍历。

对于前面提到的代价，mace 有两个压实时机：读路径上增量长度达到阈值就压实；cache 淘汰时，凡是还带着增量的叶页都先压实成基础页再换出去。压实把整条链收成一个 base：热数据本来就在内存里，冷数据压完之后再加载也只需要一次 IO。

### 身份与位置分离

备选是 page ID 直接映射到文件和偏移。

选四层身份的理由是 GC 重写必须能在不停止写入的前提下进行。如果页引用绑定物理位置，重写就要同时更新所有引用它的页，读者会看到撕裂的视图。分离之后重写只改区间图和重定位表。

代价是解析时多两步，每次读页都要走完整条链路。更重要的是它成了一个必须始终遵守的纪律：所有引用一律用逻辑地址，任何时候都不能拿文件 ID 当引用用。这不是风格偏好，是这条设计唯一的正确性前提。这还有另一个好处：ID 可以用满 64 位，既提高了数据管理上限，也不用关心 ID 回绕的问题。

### bucket 作为自治单元

备选是全局单一大索引，用 key 前缀区分 bucket。

选 bucket 自治的理由是让每个 bucket 有独立的页地址空间、索引状态、checkpoint 代、持久化边界、缓存策略、压缩策略和写入准入策略。这对混合负载很关键：一个大 value 的 bucket 和一个小 value 的 bucket 不该共享同一个内联阈值。

代价是全局服务仍然必须协调事务时间戳、WAL 流、恢复和后台维护。而且"卸载"必须严格限定为运行时操作，绝不能削弱恢复语义或中止清理语义——持久元数据和 payload 文件在卸载期间完全不变。bucket 删除也是两阶段的：先逻辑删除，物理清理放在后面，bucket 计数只在物理清理完成后才递减，这样任何一个时刻崩溃，账面都不会和磁盘对不上。

### 脏数据两代与原子分割

备选是单代脏集合加一个 checkpoint 锁，或者拷贝式快照。

选两代结构的理由是 checkpoint 期间写者不需要停。分割一次旋转所有 checkpoint 输入，之后新写者用新一代，checkpoint 持有旧一代直到发布完成。

代价是内存峰值翻倍（新旧两代同时存在），以及分割边界的推理成本。分割之后新分配的页留在新一代或者被带到下一次 checkpoint，结构链接、退休血缘和压实产生的垃圾仍然关联到仍然拥有其可达性的那一代。

前面的"内存峰值翻倍"只是理论上的，实际上不可能出现，因为后台在不停地消耗旧代的数据，前台还有流控。

### 数据优先，元数据在后

这是 mace 唯一不可协商的持久化顺序。对每个输出文件的流程是：

1. 持久化一个孤儿标记
2. 构建文件
3. 同步文件以及需要的目录状态
4. 在元数据里一次性提交区间、重定位、统计、页表和持久化边界，并清除孤儿标记
5. 发布新的运行时区间和记账状态

元数据提交之前，输出文件是孤儿，通过持久元数据不可达。元数据提交之后，它才是它所发布的那些逻辑地址的权威持有者。

反例很直接：如果元数据先指向一个还没落盘的 payload 文件就崩溃，重启后元数据指向空洞，读会失败或读到垃圾，而系统认为数据是持久的。同一条规则在纪元迁移里也成立——新纪元的文件必须先有持久的目录项，宽度变更才能被记录下来。

代价是多一次目录同步，以及崩溃后需要清理孤儿文件。孤儿文件本身是持久标记，清理只能通过这些标记驱动，不能靠扫描目录猜。

### 中止清理：重写而不是撤销

备选是给每个操作实现逆操作。

选重写的理由是代价。撤销要为每一种操作类型写逆操作，等于每次更新都写双份 WAL 记录，mace 选择用稍微复杂的页重写换更小的写放大。重写还顺带回收了空间——它本来就要重写页面，把被中止的版本从新写的那一版里去掉，这不增加额外动作。

至于"让被中止的版本不可见"，那是 abort-clean 要做的事，不是选它的理由：版本历史已经保证了中止版本不会进入查询结果，重写是为了把这些字节真正收回来。一个修改过的事务中止时，只需要保留三样东西：中止这个事实本身、它当时占用的那段 WAL、以及它碰过哪些 bucket。

代价是 O(受影响页数) 的写放大，加上一个两阶段的收尾。先重写页面，并让每个受影响的 bucket 完整地做一次 checkpoint，中止事实和 WAL 保留一直挂着；等重写出来的页真正落盘、可能持有旧页镜像的读者都读完之后，才能把任务和保留一起撤掉。整个过程里被中止的版本始终不可见——不可见性不依赖清理是否已经做完。

### 恢复的三个独立边界

恢复用三个独立的 WAL 相关边界，加载和推进都各自独立：

- **bucket 持久化边界**：某个更新是否已经持久在 bucket 数据里。这是 redo 的判定门，而且是唯一的门。
- **checkpoint 提示位**：WAL 分析可以从哪里开始。
- **回收边界**：哪些更老的 WAL 文件已经被删除。

备选是用单一的"检查点位置"，但那样恢复无法区分"这个更新已经在页里了"和"这个更新的 WAL 还在"。分开之后每个边界可以按自己的节奏推进。

代价是跨阶段的陈旧值风险。一个值可能在构造时被读取，然后后续阶段把它的持久来源推进了，于是它就过期了。我把这类问题单列成一条静态审查要求：每个不变式都要从当前状态重新推导，不能从它最初被设置的地方推导。

启动顺序在设计文档里有完整的步骤，关键点是两条：恢复必须在任何前台事务或只读视图准入之前完成；必须把从 WAL 重建出来的中止清理工作排空之后，运行时的 checkpoint 记录和启动后的 WAL 回收才真正成立。

## 开放问题与被放弃的方案

除了前面那些取舍，我还想记下几个被放弃的方案，避免以后有人重新提一遍。

**撤销式回滚**。最早的想法是给写入和删除都实现逆操作，中止时回放。放弃的原因是 WAL 记录的写放大问题。叠加上 WAL 是在 leaf node 持有锁期间写入的（虽然是拷贝到 buffer 中），多写数据就多占用锁的持有时间。

**按分组维护的已解析前缀**。曾经设想过：可见性有一个分组局部的已解析前缀，因此可以有一条跨越"未决空洞"的前缀边界。后来放弃了，因为可见性判断并不依赖这种分组局部的前缀证明，前缀边界本身没有意义。现在是按事务精确查表，未决空洞的可见性由安全水位和精确结果两条规则覆盖。

**WAL 格式升级协议**。曾经有一条规则把"正常退出后不依赖 WAL"这个不变式误当成数据格式升级协议，后来删掉了，因为当前的 payload 文件只有一个版本，根本没有格式升级这回事。

WAL 格式的当前立场是单向演进：新增的记录类型（比如合并操作数的载荷）不需要迁移屏障，因为只有更新的二进制才会去打开写入了新载荷的目录。代价是这个目录从此只能由具备该能力的二进制打开，不支持降级。这条边界只适用于记录外框不变的加法式变更；改记录外框本身，仍然要求先达到一个不依赖 WAL 的持久状态。

## 不变式怎么被守住

上面每一个取舍都对应一条必须成立的规则，而且几乎每条都横跨多个模块——写路径、checkpoint 和读路径一起构成一条，元数据发布、恢复和 GC 又构成一条。这类规则没法指定一个归属函数，硬指定会误导 review。

所以 mace 把它们放进一个独立的机器可读台账，这个台账的第一条设计决定是：**用"五种后果"当准入标准**。

### 准入标准：五种后果

一条规则要进台账，必须能说出违反它会造成哪一种后果：

- **数据丢失**：已经确认提交的数据丢了
- **崩溃安全**：崩溃后重开得到一个不一致、或者根本打不开的库
- **空间泄漏**：不可达的字节永远收不回来
- **可见性**：读者看到了不该看到的，或者丢掉了该看到的
- **并发**：数据竞争、死锁、活锁

说不出来就不进。API 形状、工具行为、内存预算、测试信号、代码风格全部推到设计文档或者代码注释里。

这条标准比看起来更有约束力：它逼着每条规则落到"操作者能观察到什么"上。"这个不变式很优雅"不是理由，"违反它会让一次读返回一个已被删除的键"才是。现在台账里 31 条规则按各自保护的东西分组排布：可见性 10、数据丢失 8、空间泄漏 8、崩溃安全 4、并发 1。

### 一条规则长什么样

一条规则 = **一个强制边界，加上共享这个边界的那些规则**。当几条规则其实由同一次分割、同一个事务、或者同一个发布窗口保证时，它们合并成一条——拆开的话，同一个反例会在两个地方各写一遍，读的人得自己发现它们是同一件事。

每条规则记四样东西：规则本身（要写到能拿去和代码对质）、违反后果（用后果自己的语言写"坏了会看到什么"）、锚点（一到三个仓库内的文件路径）、复现测试（一个测试名，或者 `none`）。

两个细节是刻意的。锚点只写路径不写行号，否则每次编辑都要改台账，台账的更新就变成噪音。复现测试允许是 `none`：没有测试的不变式是诚实的，一个什么都不验证的测试不是。

台账早期版本还记过观察点、见证代码、验证器、规则类别、置信度、失败症状这些字段。它们被删掉了，原因很具体：它们把台账变成一份测试索引加一份代码坐标清单，每次重构都要重写一遍，结果是不变式本身被自己的记账埋掉了。上一轮重构就是这样砍掉了过半条目——一部分折进覆盖同一件事的幸存者，一部分移出去放到设计文档、模块文档或代码注释里，没有一条规则被静默丢弃。

### 什么时候动台账

只有三种情况：不变式变了、锚点真的挪了、或者一条规则被退休。

**代码改动本身不是理由。** 一次重构可以重写很多文件而不碰台账——只要它没有改变任何不变式。反过来，一次改动如果动了某条规则所依赖的边界，就必须在同一批改动里把它降级，或者明确宣布它不再成立。

一条规则靠"被依赖"获得确认状态，不靠"写得好"。要撤掉一条规则，是把它移进退休记录并写明原因，而不是删掉；把一条规则折进另一条也算一次退休，要写清幸存者和理由——这样台账可以变小，但推理不会丢。

### 没有测试时怎么验

读规则本身，然后拿它的违反后果里的那个反例往当前代码上套：如果代码仍然让那个状态不可达，这条规则还立着；如果不再如此，那要么是代码退化了必须修，要么是这条规则已经不是我们想要的，得重写或者退休。

这也解释了为什么违反后果要写成"操作者视角的后果"而不是"技术上哪里错了"——它是给人当反例用的。

### 台账之外

台账只管不变式。常规测试按触及的边界选，不做全量扫；崩溃窗口用故障注入，在恢复流程的确定同步点上人为制造崩溃，验证重启后的一致性——这是最关键的一层，因为持久化顺序的 bug 只在崩溃时暴露。这些验证机制连同它们的信号（一轮回收完成要可观测、故障注入的命中要可计数）都留在各自的代码和测试里，不进台账：它们是工具契约，不是不变式。

另有一个只读的离线检查器，不启动引擎，扫描一个数据库目录，报告每一处损坏且只报告一次。它和在线路径读同一份元数据，但走可失败返回的解码路径——在线路径遇到解不开的记录会直接终止进程，因为那时候已经没有可靠的继续方式了。
