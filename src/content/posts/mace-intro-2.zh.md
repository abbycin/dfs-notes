这篇文章回答的问题是：mace 为什么是这个形状，以及每个形状的代价是什么。

- 想知道 mace 怎么用、多快，看 [README](https://github.com/abbycin/mace)
- 想改 mace 的代码，看 `docs/design.md`（流程规范）和 `docs/constraints/registry.yaml`（不变式台账）
- 想判断一个改动该不该做，看这篇文章

## 设计目标与优先级

先说清楚 mace 不追求什么，因为不追求的东西比追求的更能约束设计。

mace 是嵌入式引擎，单进程，不做分布式，不做 SQL，不做多租户隔离，也不做跨节点的副本或共识。这些不是"以后再做"，而是明确排除：一旦引入节点间通信，前面所有关于崩溃窗口的推理都要重写。

在剩下的目标里，优先级是这样的：

1. **崩溃安全与数据不丢**。这是唯一不能妥协的。任何性能优化如果要求放宽持久化边界，直接否决。
2. **快照隔离的语义正确**。已提交事务在崩溃后必须仍然可见，已中止事务必须仍然不可见。
3. **吞吐与延迟**。在 1、2 不被破坏的前提下优化。参考 README 里的对比表。
4. **实现简单**。这条排最后，但它是个真实的约束：mace 的全部代码约 45k 行，再加一层抽象就超出了一个人能完整掌握的范围。

第 1 条的体现之一是持久化选项默认开启，也就是每次提交都要求 WAL 真正落盘。另一个体现是正常退出时，即使全程用的是宽松模式，最后一次 checkpoint 仍然对所有输出文件做完整同步。运行中可以放松，退出时不能——因为退出之后再没有 WAL 可以指望了。

## 真正的难点在哪里

不是索引，不是事务，是**几个阶段之间的状态交接**。mace 里几乎所有难的地方都是"阶段 A 读到的值，在阶段 B 之后已经过期"这一类问题。

### checkpoint 收集的是可达集，不是脏集

这一节是我在 mace 里最想讲清楚的一个取舍，因为它决定了 checkpoint 到底是什么。

一个直觉的做法是：checkpoint 把所有脏页收集起来写出去。这在页是不可变的、且写者不会改变页的可达性的模型里是成立的，比如 LSM 树的 memtable。但 Bw-Tree 不行。一个页变脏之后、在 checkpoint 跑到它之前，它完全可能已经不可达了：增量链被合并、父节点的链接被换成新页、节点分裂或合并产生了新的页镜像。这些页如果照写，就是纯垃圾——写放大白付，而且它们会在下一次 GC 里被当成需要回收的空间。

所以 mace 的 checkpoint 收集的是**从脏根出发可达的页集合**，不是脏页集合。这个区别不是实现细节，它换来了两个东西：写集只包含真正会被再次读到的页，以及一个准确的"哪些页已经被持久化"的结论。

那为什么不干脆用 arena？既然页是按单调递增的逻辑地址分配的，把脏区整段刷出去不就不用遍历了吗？三个原因，第三个是决定性的：

1. **mace 的内存页不是 arena**。每个页是独立分配、带引用计数、长度各异的对象，散落在堆上，没有"脏区"这个连续区间可刷。
2. 整段刷会把上面那些已经不可达的页一起写出去，写放大直接翻倍。
3. **持久化边界是可达性的函数，不是脏度的函数。**

第 3 条是核心，下面单独说。

#### 持久化边界必须跟着写集走

mace 用一个按写者组记录的**持久化边界**（下面就叫 frontier）记录"每个写者组的更新推进到了哪个位置"，恢复时拿它和脏页逐条比较，决定一条 WAL 更新是已经落进页里了，还是需要重放。

这个 frontier 的定义是"已经被写出去的页所覆盖的最大位置"。注意是**写出去的页**，不是脏页。

这个区别是致命的。如果 frontier 按脏页算，会出现两种结局，都很糟：按超集算，那它声称覆盖了一些根本没写进持久文件的 WAL 位置，崩溃后这些更新被跳过，数据丢了；按实际写的算，那你还是得知道实际写了什么，还是得遍历。

垃圾地址的记账也一样。它只能从被写出的那些基础页的退休链里提取，并且要排除本次 checkpoint 期间新产生的垃圾和越过快照边界的地址。这些判断全都依赖"哪些页被写了"。

所以准确的表述是：**遍历不是一个收集页的技巧，它是同时产出写集、垃圾集、持久化边界和解除映射集这四样东西的机制。** 任何绕开遍历的方案，缺的不是性能，是正确性——为了算对这四样东西，还是得遍历一遍。

#### 不冻结写者的前提

遍历能在写者照常写入的前提下进行，靠的是一个快照边界：切刀时记下当时已分配到的最大逻辑地址，遍历时遇到比它大的地址，就知道这个页是切刀之后新分配的，留给下一代 checkpoint 处理。

这也是整段 flush 做不到的事——切刀之后新分配的页根本没有对应的连续区间可刷，你必须知道"哪些是这一代的"，而这正是遍历在做的事。

代价是遍历要读每个存活页的头部才知道往哪走，比单纯枚举多一轮随机读。而且从切刀到遍历完成，同一次 checkpoint 的写者还能继续产生新页，所以要等这一代的在途写者全部退出，才能确定这一代的实际体量。

切刀本身的原子性是另一层约束。脏页集合、退休链、垃圾地址、脏根、解除映射标记、在途写者状态，这些必须作为一个整体旋转，不能分两次。切歪了的后果是静默的数据丢失：一个写者跨越了切刀，它的页可能既不在旧代也不在新代；一个存活页从两代里都消失了，checkpoint 会认为它已经持久化，实际它只是从内存里消失了。两种情况都不会当场报错，只会在下一次崩溃恢复或者下一次读的时候暴露。

这一节的代价总结成一句：可达性遍历让 mace 少写很多垃圾页，代价是 checkpoint 比枚举脏页贵，而 frontier 和垃圾记账的正确性完全依赖这次遍历没有漏项。

### GC 和 checkpoint 会同时修改同一份记账

垃圾回收的部分重写要挑 victim 文件、读它们的非活跃记录、生成替换文件、发布替换记账、然后删旧文件。与此同时 checkpoint 也在产生新的垃圾地址，也需要更新非活跃位图和文件统计。

难点在于"归属"：checkpoint 在重写进行期间新退休的那些逻辑地址，应该记在旧文件的账上，还是记在新文件的账上？

常见的解法是加一把交接锁，一方交接完另一方才能动。但这把锁会横跨整个重写过程，而重写可能持续很久，期间所有 checkpoint 都被阻塞——写者的脏数据无限堆积，反过来又推高重写压力。

mace 的选择是不加锁，靠"谁持有归属登记"来判定：重写在读取旧文件的非活跃状态之前就登记自己对这些文件的归属，checkpoint 遇到已被登记的文件时，走一条和普通路径不同的分支——重新解析逻辑地址、更新旧文件的账、把这个地址挂起来等重写方接收；重写完成后，已经被复制过去的地址再转到新文件的账上。归属状态只有在持久元数据和运行时记账都指向新文件之后才释放。

代价是这个交接的正确性不再由锁保证，而由"登记先于读取"这个顺序保证——顺序错了就是空间泄漏或者统计为负，而且要跑很久才看得出来。

### 中止清理不是撤销，是重写

中止的事务不能靠反向操作撤销，mace 的做法是把受影响的版本物理删掉，靠重写页面。这带来两个额外约束：重写完成后还需要等可能持有旧页镜像的读者排空，任务才能真正结束（WAL 保留在此之前一直挂着）；另外，一个已经卸载的 bucket 不会为了稳态清理重新加载，它的任务保持未决状态并阻塞卸载和删除完成。完整取舍见后文的决策一节。

### WAL 迁移的擦除范围

持久化选项和并发写宽度都是记录在库里的配置，改值不会拒绝打开，而是走一次纪元迁移。麻烦在于旧纪元文件的分布：请求更宽的宽度时，目标宽度独占的那些流里可能残留着上一次中断的尝试留下的文件，只按目标宽度清理会漏掉它们。所以清理范围取源宽度和目标宽度里较宽的一侧，再并上磁盘上实际存在的所有 WAL 命名空间，以及共享流。事务重放的扫描和分组校验在清理完成之前保持在源宽度上。

这条规则是踩过坑之后写进去的，之前的版本只按目标宽度清理，结果是宽度变更中断后重开，目标宽度独占的流里留下无人认领的纪元文件。

### 外部依赖的原子性假设

mace 的元数据存在 btree-store 里，整个元数据清单的发布依赖它把跨多个 bucket 的一次变更当作一个整体提交——要么全部可见，要么失败后仍然看到旧状态。这是一个外部依赖的假设，mace 没有办法只靠自己证明它，所以它在不变式台账里被标成"待复核"而不是"已确认"。

同样待复核的还有两条：一条是页表、区间和文件统计、bucket 的持久化边界必须在同一次发布里提交，崩溃后不能出现"页表说可见、边界说没落盘"这种撕裂状态；另一条是 reader 必须拒绝它不认识的 payload 文件版本。

我把这些公开写出来，而不是等 review 的时候被人问出来。

## 概念与身份模型

mace 有四层身份，这个分层是理解整个系统的关键。

| 身份 | 含义 |
| --- | --- |
| bucket ID | 一个命名 bucket 的持久身份 |
| page ID | bucket 内部某个索引页的逻辑身份 |
| 逻辑地址 | bucket 地址空间内某个持久记录的持久身份 |
| file ID | 一个 data、blob 或 WAL 文件的身份 |

解析一个已持久化的页要走三步：bucket 的页表把页 ID 映射到逻辑地址，bucket 的区间图把逻辑地址映射到某个 data 或 blob 文件，文件内部的重定位表再把逻辑地址映射到字节范围。

为什么要多这一层间接？因为垃圾回收重写改变物理位置，但保持逻辑地址不变。代价是每次持久化都要维护区间图、重定位表和每文件统计这三张表，换来的是页引用和版本历史引用在文件重写前后完全稳定——这是重写能后台进行、不需要停写的前提。

持久化状态分四个域：元数据（除 WAL 之外的一切账本）、WAL 文件（事务重放记录和 checkpoint 提示）、data 文件（索引页和结构记录）、blob 文件（大 value）。元数据是重建数据库的权威来源，data 和 blob 只有通过元数据发布才真正属于数据库。

运行时分三个域：前台的事务和只读视图、bucket 运行时（索引、缓存、脏代、checkpoint 状态）、后台服务（checkpoint 完成、恢复、中止清理、WAL 回收、payload 回收、bucket 清理）。bucket 运行时是懒加载的，打开数据库不会把所有 bucket 的索引都拉起来。

## 借鉴与偏离

mace 的索引部分来自 Bw-Tree：不可变的页镜像加增量链更新，树变更发布新的页镜像而不是原地改持久页。增量链长度达到阈值就合并，阈值是每个 bucket 的可调项，默认取节点分裂基数的一半。Bf-Tree 论文里的乐观锁耦合给了读路径的形状——读侧无锁，写侧靠乐观并发加重试。

元数据层没有自己造轮子，用的是 btree-store。data/blob 文件格式是四个区：payload 帧、logical address 区间、重定位项、文件末尾的固定 footer。footer 记录格式版本和两张表的基数与校验和，是重开文件时的发现点。

下面这些是刻意偏离常见做法的地方：

- **中止清理用重写而不是撤销**。反向操作需要为每种操作类型实现逆运算，而且和版本历史叠加后很难证明正确。mace 选择写放大换简单。
- **合并算子是纯运行时对象，永不持久化**。引擎只持有运行时句柄，不记录算子的身份，跨进程重启后的语义兼容性由调用方负责。这样避免了在磁盘格式里引入"如何表达用户自定义类型"这个问题。
- **逻辑组和物理流是两个正交维度**。多数同类引擎只有一个"并发写宽度"维度，mace 把事务事实的归属和 WAL 文件命名空间拆开了。原因见下一节。
- **关闭持久化选项时，写入系统页缓存仍然算有效**。这是选项的语义契约，不是不严谨。

## 关键设计决策

这一节是全文的核心。每条决策我给出：备选方案、最终选择、理由、代价。

### 索引：为什么是 Bw-Tree 式的增量链

备选是 LSM 树（sled、RocksDB 那条路）和传统 B+Tree 原地更新。

选 Bw-Tree 式结构的理由有两条。一是 mace 需要非阻塞的并发读，页镜像不可变让读者不需要和写者协调；二是写者只做增量追加，避免了每次更新都触发页分裂或 LSM 的压实风暴。

代价是读放大：一次点查要沿着增量链从新到旧遍历，直到找到快照可见的版本。这也是必须有合并阈值的原因——链太长就合并。另外我早期在 photondb 上踩过一个坑：合并如果不保证同一个 key 的所有版本落在同一个节点上，查找路由会出错，频繁更新的单个 key 会让某个节点体积失控。mace 的处理是把版本历史放进 key 局部的历史区域，由一个描述符记录它从哪一页哪个槽开始、有多少个版本，不同 key 可以共享同一张历史页，但各自只在自己的声明范围内遍历。

### 身份与位置分离

备选是 page ID 直接映射到文件和偏移。

选四层身份的理由是 GC 重写必须能在不停止写入的前提下进行。如果页引用绑定物理位置，重写就要同时更新所有引用它的页，读者会看到撕裂的视图。分离之后重写只改区间图和重定位表。

代价是解析多两步，每次读页都要走完整条链路。更重要的是它成了一个必须始终遵守的纪律：所有引用一律用逻辑地址，任何时候都不能拿文件 ID 当引用用。这不是风格偏好，是这条设计唯一的正确性前提。

### bucket 作为自治单元

备选是全局单一大索引，用 key 前缀区分 bucket。

选 bucket 自治的理由是让每个 bucket 有独立的页地址空间、索引状态、checkpoint 代、持久化边界、缓存策略、压缩策略和写入准入策略。这对混合负载很关键：一个大 value 的 bucket 和一个小 value 的 bucket 不该共享同一个内联阈值。

代价是全局服务仍然必须协调事务时间戳、WAL 流、恢复和后台维护。而且"卸载"必须严格限定为运行时操作，绝不能削弱恢复语义或中止清理语义——持久元数据和 payload 文件在卸载期间完全不变。bucket 删除也是两阶段的：先逻辑删除，物理清理放在后面，bucket 计数只在物理清理完成后才递减，这样任何一个时刻崩溃，账面都不会和磁盘对不上。

### 脏数据两代与原子切刀

备选是单代脏集合加一个 checkpoint 锁，或者拷贝式快照。

选两代结构的理由是 checkpoint 期间写者不需要停。切刀一次旋转所有 checkpoint 输入，之后新写者用新一代，checkpoint 持有旧一代直到发布完成。

代价是内存峰值翻倍（新旧两代同时存在），以及切刀边界的推理成本。地址边界之后创建的页留在新一代或者被带到下一次 checkpoint，结构链接、退休血缘和压实产生的垃圾仍然关联到仍然拥有其可达性的那一代。

### 数据先，元数据最后

这是 mace 唯一不可协商的持久化顺序，也是整个不变式台账里的第一条。对每个输出文件的流程是：

1. 持久化一个孤儿标记
2. 构建文件
3. 同步文件以及需要的目录状态
4. 在元数据里一次性提交区间、重定位、统计、页表和持久化边界，并清除孤儿标记
5. 发布新的运行时区间和记账状态

元数据提交之前，输出文件是孤儿，通过持久元数据不可达。元数据提交之后，它才是它所发布的那些逻辑地址的权威持有者。

反例很直接：如果元数据先指向一个还没落盘的 payload 文件就崩溃，重启后元数据指向空洞，读会失败或读到垃圾，而系统认为数据是持久的。同一条规则在纪元迁移里也成立——新纪元的文件必须先有持久的目录项，宽度变更才能被记录下来。

代价是多一次目录同步，以及崩溃后需要清理孤儿文件。孤儿文件本身是持久标记，清理只能通过这些标记驱动，不能靠扫描目录猜。

### WAL 的两个正交维度

每条 WAL 记录有两个归属维度：**逻辑组**决定事务事实、可见性、持久化边界和 checkpoint 记账年龄的归属；**物理流**决定追加、恢复和中止链遍历使用哪一组文件。逻辑组写在记录里，不从它落在哪个文件推断。

两种持久化路由因此不是"同一套机制开不同的同步开关"，而是两种物理布局：

- **宽松路由**：每个逻辑组写自己的物理流。提交只把 WAL 字节刷到文件页缓存就发布结果，没有同步代，也没有持久等待。崩溃可能丢失最近提交的事务。
- **持久路由**：所有逻辑组追加到同一个共享物理流，这个流有独立于分组流的命名空间。并发提交的终结记录和显式屏障加入一个由提交方发起的同步代，这一代封住一个流切点，同步所有字节穿过该切点的写入者以及日志目录，然后一次性完成所有目标被这个切点覆盖的提交。

拆分这两个维度带来的好处是：checkpoint 记账年龄在两种路由下都是按逻辑组算的，只有物理布局变了。所以切换持久化路由是一次纯粹的布局迁移——事务语义、持久化边界、checkpoint 记账都不用动，迁移只是把旧纪元的流回收掉、在新的文件编号高水位之上开新纪元。

代价是恢复必须扫描所有保留的物理流，不管这次打开请求的是哪个路由，否则会漏掉另一个命名空间里的历史。持久路由还有一个反直觉的细节：WAL 缓冲轮转和普通 flush 都不推进"已持久到哪里"，只有一次成功的同步代才推进。

### 中止清理：重写而不是撤销

备选是给每个操作实现逆操作。

选重写的理由是版本历史已经让旧版本不可见，不需要额外的撤销通道；而且重写顺便回收了空间。一个修改过的事务中止时，只需要保留三样东西：中止这个事实本身、它当时占用的那段 WAL、以及它碰过哪些 bucket。

代价是 O(受影响页数) 的写放大，加上一个两阶段的收尾。先重写页面，并让每个受影响的 bucket 完整地做一次 checkpoint，中止事实和 WAL 保留一直挂着；等重写出来的页真正落盘、可能持有旧页镜像的读者都读完之后，才能把任务和保留一起撤掉。整个过程里被中止的版本始终不可见——不可见性不依赖清理是否已经做完。

### 恢复的三个独立边界

恢复用三个独立的 WAL 相关边界，加载和推进都各自独立：

- **bucket 持久化边界**：某个更新是否已经持久在 bucket 数据里。这是 redo 的判定门，而且是唯一的门。
- **checkpoint 提示位**：WAL 分析可以从哪里开始。
- **回收边界**：哪些更老的 WAL 文件已经被删除。

备选是用单一的"检查点位置"，但那样恢复无法区分"这个更新已经在页里了"和"这个更新的 WAL 还在"。分开之后每个边界可以按自己的节奏推进。

代价是跨阶段的陈旧值风险。一个值可能在构造时被读取，然后后续阶段把它的持久来源推进了，于是它就过期了。我把这类问题单列成一条静态审查要求：每个不变式都要从当前状态重新推导，不能从它最初被设置的地方推导。

启动顺序在设计文档里有完整的十二步，关键点是两条：恢复必须在任何前台事务或只读视图准入之前完成；必须把从 WAL 重建出来的中止清理工作排空之后，运行时的 checkpoint 记录和启动后的 WAL 回收才真正成立。

## 开放问题与被放弃的方案

上面提到的那三条待复核规则就是公开的开放问题。除了它们，我还想记下几个被放弃的方案，避免以后有人重新提一遍。

**撤销式回滚**。最早的想法是给写入和删除都实现逆操作，中止时回放。放弃的原因是它和版本历史、大 value 分离、页合并三条机制都有交互，每增加一种操作类型就要证明一遍。改成重写之后，中止的正确性论证只依赖"哪些页被重写了"，而不依赖操作的可逆性。

**按分组维护的已解析前缀**。曾经设想过：可见性有一个分组局部的已解析前缀，因此可以有一条跨越"未决空洞"的前缀边界。后来放弃了，因为可见性判断并不依赖这种分组局部的前缀证明，前缀边界本身没有意义。现在是按事务精确查表，未决空洞的可见性由安全水位和精确结果两条规则覆盖。

**WAL 格式升级协议**。曾经有一条规则把"正常退出后不依赖 WAL"这个不变式误当成数据格式升级协议，后来删掉了，因为当前的 payload 文件只有一个版本，根本没有格式升级这回事。

WAL 格式的当前立场是单向演进：新增的记录类型（比如合并操作数的载荷）不需要迁移屏障，因为只有更新的二进制才会去打开写入了新载荷的目录。代价是这个目录从此只能由具备该能力的二进制打开，不支持降级。这条边界只适用于记录外框不变的加法式变更；改记录外框本身，仍然要求先达到一个不依赖 WAL 的持久状态。

## 不变式怎么被守住

上面每一个取舍都对应一条必须成立的规则，而且几乎每条都横跨多个模块——写路径、checkpoint 和读路径一起构成一条，元数据发布、恢复和 GC 又构成一条。这类规则没法指定一个归属函数，硬指定会误导 review。

所以 mace 把它们放在一个独立的机器可读台账里，每条规则记录：它说了什么、什么改动应该触发重新 review、现在哪些代码路径在维护它、坏了会看到什么症状、现在有什么验证。规则分四类：局部规则、跨阶段协议、依赖外部契约的规则，以及靠多条路径共同维持的涌现规则。其中跨阶段协议占绝大多数。

状态是有梯度的。除了"已确认"，还有"待复核"——很可能成立但证据弱、陈旧，或者相关的代码改动过，必须重新 review 一次。硬规则是：一次改动如果碰了某条已确认规则的 review 触发点，就必须在同一批改动里重跑它的验证、把它降级成待复核、或者明确宣布它不再成立并写清原因。不允许"改完了但没人再看"。

验证分三层。常规测试按触及的边界选，不做全量扫。崩溃窗口用故障注入，在恢复流程的确定同步点上人为制造崩溃，验证重启后的一致性——这是最关键的一层，因为持久化顺序的 bug 只在崩溃时暴露。默认构建里可观测性代码是零，指标系统只在显式开启编译特性时才存在，而且指标身份是固定基数，不允许出现无界的 bucket、key 或事务标签。

另外有一个只读的离线检查器，作用是在不启动引擎的情况下扫描一个数据库目录，报告每一处损坏且只报告一次。它和在线路径读的是同一份元数据，但走的是可失败返回的解码路径——在线路径遇到解不开的记录会直接终止进程，因为那时候已经没有可靠的继续方式了。
